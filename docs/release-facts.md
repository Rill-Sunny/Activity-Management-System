# 可用于简历与面试的技术事实

以下表述限于本机工程验收，不代表线上流量或商业支付平台。

1. 基于 Java 23、Spring Boot 3.5.16、MyBatis 和 MySQL 构建模块化单体后端，完成 FREE 预约、PAID 两种配座、逐票退款、GIFT 独立资源、多 SKU 商品及部分售后、持票限定商品联动、场次改期与活动/场次取消。模型包含 42 张应用表，保留成交快照、历史、任务与逻辑关联巡检。
2. 使用 MySQL 行锁、条件更新、固定锁顺序、整事务重试与持久幂等保障库存、座位和共享限购。AT-12 验证后一 SKU 缺货时前一扣减回滚，旧单在回滚后独立安全关闭；同事件消费与多事件售后均防重复效果。最终测试计数与源码见 [发布验收报告](../qa/reports/day30-final-acceptance.md)，不把跳过算作通过。
3. 实现 Redis generation 缓存及持久失效补偿、RabbitMQ + Transactional Outbox、Consumer 幂等和 DLQ 重放；通过 Docker 双实例、Prometheus/Grafana/Tempo 和 k6 验证。Day 28 实测 Redis 恢复 6.80 秒、RabbitMQ 恢复 16.22 秒，ACK 前进程退出后恢复 20.39 秒；这些是该轮环境结果，不是 SLA。

## 可引用的性能数字及边界

Day 27 热读取 10/50/100 VU 各 120 秒预热、300 秒采集，约 2169/1970/1715 RPS，p95 约 28/95/207 ms，技术错误为 0。测试每个 VU 同时读 Activity 和 Product，不能把吞吐写成成功支付 TPS。

取消批次从每 tick 一页改为最多四个独立小事务页，相同 100 笔退款夹具收敛 54.03 → 36.64 秒，有效退款 TPS 1.85 → 2.73。没有扩大单事务或放宽业务约束。

热点支付 S04/100 VU 的 200 请求中 96 成功、66 业务拒绝、38 技术错误（19%），p95 5600.83 ms。根因是热点资源行串行竞争占用每实例 10 个 Hikari 连接，触发 3 秒连接获取超时。部分 50 VU 交易也未达 1 秒参考值。面试中应如实说明容量边界及后续削峰/缩短持锁时间的工作，不能宣称高并发支付全档通过。

## 一次值得复盘的缺陷

Day 29 HTTP 演示发现商品订单响应遗漏 orderItemId，而发货、收货和售后都必须传该 ID。旧集成测试直接查询数据库取得 ID，掩盖客户端不能完成闭环的问题。新增纯 HTTP 获取 ID 的回归先失败，再最小补齐响应字段；保留原始失败、修复快照与完整商品模块复跑证据。

AI 用于辅助代码审查、脚本实现、失败定位、回归执行及报告核对；验收结论来自真实日志和提交后的数据库记录，不来自生成的预期结果。
