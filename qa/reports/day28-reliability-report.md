提交结果未知的用例明确含有人工注入的“确认丢失”异常，它验证应用面对已提交但客户端收到错误时的处理，不声称在网络层精确截断了 COMMIT 响应包。进程退出用例使用 `Runtime.halt(77)`，不运行正常关闭钩子；故障代码仅位于测试辅助程序。

Publisher confirms 与消费者 ACK 分别覆盖发布和消费环节，连接断开时未确认消息可能重新入队，因此最终以数据库唯一效果及消费记录判断幂等。[RabbitMQ 官方说明](https://www.rabbitmq.com/docs/confirms)

## 修复记录

扩大数据库对账范围后，发现原锁重试测试夹具只插入订单主表，未准备订单明细，造成订单金额对账异常。现改为通过真实下单 API 创建合法夹具，保留原来的锁等待和死锁注入。修复专项 14/14 通过，包含断连 2 项、锁重试 3 项、多 SKU 4 项和缓存指标 5 项；这属于开发期专项结果，不代替最终全仓和真实停机验收。

同时补充 Redis 错误指标，将超时、连接失败、其他错误分开，并限制标签枚举范围。普通 cache miss 不再充当 Redis 故障次数。

首次 F01 的独立 JVM 已在 Publisher Confirm 后按预期退出 77，但恢复脚本失败：PowerShell 将传入 .NET 字符串参数的 `$null` 绑定为空串，使原本不存在的环境变量成为空变量，覆盖了 Compose `--env-file` 中的有效配置。已用最小复现确认，并改为显式移除原本不存在的 `Env:` 项；同样修复原生测试运行器的清理逻辑。该失败现场、崩溃边界和人工恢复对账保留，不计为 F01 通过；完整复跑结果另行记录。故障执行器也增加失败原因落盘，避免恢复异常掩盖原始失败。
