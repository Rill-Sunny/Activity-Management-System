## 修复与设计重点

取消的 Activity X 与原支付的 Activity S 协调；单场次取消也覆盖活动范围限定商品的资格检查。取消入口不锁 Order，后台处理不持有生命周期 X，避免与支付形成反序等待。

自动退款通过内部 MANDATORY 入口复用原资源事务，校验 CANCELLATION_REFUND 政策和取消范围，不依赖用户 JWT。旧申请以 CANCELLATION_SUPERSEDED 结束，原报价、逐票金额、改期历史与响应保留；新取消退款和任务成功一次提交。

Item 成功与批次汇总分开，扫描器修复“最后一项已经成功、进程在汇总前退出”的情况。人工重试只改变失败项目，不重开成功项目；旧认领令牌不能恢复已接管任务。

新增商品并发用例首轮全仓预期写为 409，但既有 PRODUCT_QUALIFICATION_DENIED 契约为 403。实际取消后付款已被拒绝；已修正为断言精确业务错误码，同时保留 SKU 未扣和订单未成交验证，不修改既有接口为迁就测试。

全仓另一个失败来自旧 ActivityQuery 测试仍要求 CANCELLED 返回 404。按本日公开取消状态需求，更新为 200 并断言真实 CANCELLED；DRAFT、FINISHED 隐藏规则保持。没有把该契约变化算作退款业务失败。

代码复核发现原白名单服务只校验 Activity，单独取消 Session 时 Activity 仍 PUBLISHED，可能继续编辑该场次名单。现改为获得 Activity 根锁后再读取 Session S 并要求 SCHEDULED，避免复用等待前的发现结果。新增四种名单操作拒绝与真实锁等待测试，其他正常场次仍可维护。

补测中出现 24 个失败，均来自新增白名单测试的清理遗漏：父夹具删除 Activity/Session 后残留名单，导致后续孤儿对账逐个失败。补上本隔离库的 whitelist_member、whitelist_config 清理；不删除对账查询或放宽断言。

内部退款最初使用 cancel:eventId:ticketId 作为请求键，买家可预占相同文本，旧请求即使终止仍会占用唯一键。现改为内部随机 UUID；幂等依据是持久化 Cancellation Item 及其与退款效果同事务的成功标记。回归通过普通退款 API 预占旧格式键，再执行取消，验证全额自动退款仍可成功。
